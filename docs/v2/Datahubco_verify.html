一、结论

手册里的数据大部分能用，但不是"都可以"。实测 81 个接口中 60 个正常返回数据， 10 个需要改参数或只能在特定条件下使用，11 个完全不可用。

  • 8 个"行业特色"接口全部不可用（tmt_twincome / tmt_twincomedetail / bo_monthly / bo_weekly / bo_daily / bo_cinema / film_record / teleplay_record），网关转发后上游统一返回"请指定正确的接口名"。且官方 2026-10-10 新版指引已把这 8 个标注为"先确认，勿探测"。
  • pro_bar 确认不支持——网关直接拒绝，与手册说明一致。
  • stk_factor_pro 当前不可用——上游 8 秒超时，连续 4 次 HTTP 502。
  • 11 个接口手册给的示例参数是错的，照抄会拿到空结果（详见第四节）。
  • 发现一个静默数据缺失缺陷：margin_detail 的本地缓存快照只含上交所，深交所和北交所数据整体丢失（详见第三节 P0）。

三、发现的问题（按严重度）

P0margin_detail 本地缓存缺深交所、北交所数据——静默少给数据

同一个请求，命中本地缓存和强制回源拿到的是两套数据，而且网关不会报任何错：

GET margin_detail?trade_date=20260930&limit=5000
  → n=2001  src=sqlite/LOCAL   市场分布 {'SH': 2001}          # 只有上交所

GET margin_detail?trade_date=20260930&limit=5000&fields=...（显式 fields 改变缓存键）
  → n=4454  src=upstream/MISS  市场分布 {'SH':2001,'SZ':2108,'BJ':345}   # 完整

连续 4 次相同请求稳定返回 2001 条，不是偶发。缺的是 2108 只深市标的 + 345 只北交所标的， 平安银行（000001.SZ）就查不到。对照组 daily、daily_basic 的本地快照是完整的（SH 2102 + SZ 2898）， 说明这是 margin_detail 这一条快照的构建缺陷，不是整体缓存策略问题。

影响：任何按 trade_date 拉全市场融资融券明细的客户，会静默丢掉 55% 的数据。 这比直接报错危险——程序不会失败，只是结果错了。

规避：显式传 fields 强制回源；或按 ts_code+日期区间查询。同时建议向服务方反馈。

P18 个行业特色接口上游不可用，且官方标注"勿探测"

8 个接口返回 HTTP 400 / code 40101 / msg=请指定正确的接口名，help.reason=upstream_parameter， retry_same_request=false——是上游 Tushare 拒绝，不是网关白名单问题。

对照组说明这不是接口名拼错：换名字试（bo_monthly_amount、movie 等）会返回完全不同的错误 code=400 unknown api_name。说明网关认得这些名字、确实转发了，是上游没有。

注意：线上新版指引已把这 8 个标注为「先确认，勿探测」，示例代码带 service_confirmed=False 守卫，并注明"该接口权限或业务状态未证实当前可用；本示例不能作为自动探测指令"。 本次验证按桌面手册做了一次性最小请求，结论与官方标注一致，后续不应再重复探测，需要用时先向服务方确认。

P1stk_factor_pro 上游超时

连续 4 次（单日、区间、两个交易日）均返回 HTTP 502 / code -1 / Operation timed out after 8000 milliseconds。 官方标注为「目录接受，有条件可用」，但当前实测不可用。若业务依赖前复权技术因子，需准备替代方案。

四、其他实测结论

本地缓存生效14 个接口命中本地 SQLite / Redis 快路径，其余回源上游 分页上限网关强制单页上限 5000 行（limit=6000 返回 400 query limit is too large），手册说法一致 鉴权X-API-Key 请求头有效，无 401 空结果 vs 报错区分清晰：code=0 且 items=[] 表示无匹配数据，与 HTTP 4xx/5xx 完全分离 stock_basic不在手册 80 清单内，但线上目录已收录（第 84 项，状态「目录接受，有条件可用」），实测可用

五、建议

  1. 先修 margin_detail 的取数逻辑，这是唯一会造成"数据错了但没人知道"的问题。别信本地缓存，显式传 fields 或改用 ts_code+区间，同时报给服务方。
  2. 别把 8 个行业特色接口排进开发计划，需要电影票房/台系营收/剧本备案数据时先找服务方确认，并准备替代数据源。
  3. 把手册示例全部按第四节表改一遍，别直接复制示例代码。
  4. 改用线上版指引，注意新版对探测行为的限制。
  5. 生产环境把 API Key 移到环境变量，别硬编码——当前密钥已出现在桌面文本和多个脚本里。
验证方法：按手册第 5 节逐接口构造最小可用请求（limit=5），记录 HTTP 状态码、业务 code、返回条数、 X-Data-Source/X-Cache 响应头；失败项按「参数错误 / 无权限 / 无数据 / 网关不支持」四类做二次归因并换参重试。 原始结果见 results.json、results_pass2.json。
